\section{The question}
\label{sec:introduction}

A plan or prediction is useful only while its assumptions hold.  In a
multi-robot system, the component using a result may be several steps away from
the component that produced it.  It may even be on another robot, with a
different clock and an older view of the world.  The question behind this note
is simple: \emph{what should travel with a result so the receiver can decide
whether it is still valid?}

A mission planner, motion predictor, middleware layer, and safety controller
answer different questions.  A mission synthesizer may guarantee a temporal
goal within a declared context.  A planner may find a feasible route for a
particular state and model.  A predictor may forecast peer motion over a
horizon.  None of these claims automatically tells the next component whether
its own assumptions are satisfied.

This matters as robot stacks combine task allocation and motion coordination
\cite{gerkey2004mrta,choi2009cbba,sharon2015cbs} with language-conditioned
planning and learned prediction \cite{mandi2024roco,obata2025lipllm,li2026llmmrs}.
The newer components still depend on physical, timing, and deployment
assumptions.  Where inference runs adds another tradeoff: an on-board estimate
is close to the controller, while a remote estimate may use more data but arrive
later \cite{kehoe2015cloud}.  At lower layers, ROS~2 and the Data Distribution
Service (DDS) carry state and commands, and runtime-assurance or barrier-based
controllers may override a decision before actuation
\cite{macenski2022ros2,omg2015dds,desai2019soter,wang2017barrier}.

The multi-robot case adds a practical difficulty.  Robot $r_i$ can make a
locally reasonable decision using stale peer state and invalidate robot
$r_j$'s route, resource claim, or safety margin.  Joining, leaving, restarting,
and recovering from a network partition can also invalidate assignments while
messages remain syntactically correct.  I distinguish \emph{vertical}
interfaces within a robot from \emph{horizontal} interfaces between robots or
distributed services (\cref{fig:command-path}).

Existing work addresses parts of this question through mission contracts,
quantitative mission assurance, component contracts for the Robot Operating
System (ROS), compositional reasoning for dynamics, monitoring, and safety
switching
\cite{mallozzi2020crome,chaki2013assurance,luckcuck2026compositional,
sharf2021dynamical,ghaffari2024rosmonitoring,desai2019soter}.  I reviewed these
approaches with three questions in mind:
\begin{enumerate}
  \item What does each approach protect, and which assumptions and guarantees
    does it represent?
  \item How are those claims combined, checked, enforced, or repaired, and
    what evidence supports them?
  \item What remains implicit when a result crosses a component or robot
    boundary, and what would make those assumptions checkable?
\end{enumerate}

\subsection*{What this note contains}

I group the reviewed approaches by what they protect, then compare their
coverage of interface obligations (\cref{sec:taxonomy,sec:gaps}).  From the gaps,
I propose a reference framework for recording validity checks, evidence, and
recovery rules (\cref{sec:framework}).  A temporal admission condition for peer
state makes the timing and estimation fields concrete and shows when an
on-board estimate can be preferable to a more accurate remote estimate.  A
failure taxonomy and command trace show how to assign checks and recovery
authority along the command path (\cref{sec:attribution,sec:trace}).

The useful connection is between interface design and the decision that uses
the data.  The peer-state calculation shows why a time stamp, a clock-error
bound, or an estimation-error bound belongs in an interface: each changes the
margin available to the receiving robot.
